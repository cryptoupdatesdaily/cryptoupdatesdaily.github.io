How to trace an unknown token approval to its first grant

Find an unknown token approval's transaction by matching chain, token, owner and spender to Approval events, then inspect receipts to identify its first grant.

By Blockchain Today EditorialNov 18, 2026 · 13:53 UTC5 min read

An unfamiliar ERC-20 approval can be traced to its original transaction when the chain, token, owner and spender match a historical Approval event and its receipt. A current allowance tells you what permission exists now; transaction history can show how it began and changed. You need the public wallet address and the relevant network to start.

Match the approval to its onchain history

  1. Record the permission’s identifying details. Copy the chain and full token, owner and spender addresses from revokecash. Use revokecash here to inspect and manage the approvals your wallet has granted to smart contracts. Keep the full addresses: a familiar token name or shortened address is not enough to distinguish contracts. Make sure the explorer you use is set to the same chain, since an address can refer to different contracts on different networks.
  2. Follow matching approval transactions. Open the approval history and follow transaction links that match the token, owner and spender. An ERC-20 Approval event records those addresses and the approved value. The event’s transaction hash points to the transaction that emitted it; [Etherscan Logs](https://kb.etherscan.com/what-is-event-logs) describes how explorers expose transaction event records. A current allowance is useful for identifying what remains permitted, while the history is needed to trace earlier changes.
  3. Use token logs if the history is incomplete. Search the token contract’s logs on the matching chain for Approval events. Compare the event’s owner and spender fields with the addresses you recorded, then note the transaction hash and log index. The log index matters: one transaction can contain multiple approval events, including events for different spenders or repeated updates. Save the log index alongside the hash so you can point to the exact event, not just the larger transaction that contains it.
  4. Inspect the transaction receipt and event. Open each matching transaction and confirm that it succeeded. Then verify that the event was emitted by the token contract you are tracing and that its owner and spender match. Read the value as recorded in the event; compare it with the token’s units if the explorer displays a raw integer. The receipt connects the event to a successful onchain transaction, while the event fields establish which permission changed.
  5. Account for permit transactions. A permit can authorize an allowance through a signed message, and its execution may be submitted by a relayer. In that case, the transaction sender can differ from the wallet listed as the approval owner. Inspect the logs alongside the decoded input: the input may help explain the permit call, while the Approval event confirms the emitted owner, spender and value. An explorer may show an unfamiliar method name when it cannot decode the contract call, so use the event fields and receipt rather than relying on the method label alone.
  6. Order the matching events and identify the first grant. Sort the matching events by block and transaction order, using their hashes and log indexes to keep events within the same transaction distinct. Find the earliest event that sets a positive allowance for that owner and spender; this is the first grant in the history you found. Later matching events may change the value, including updates that replace an earlier allowance. In a constructed case, a wallet owner sees a large current allowance to an unfamiliar spender. Matching the owner and spender across dated logs reveals the first positive grant and later changes, giving the owner a specific transaction to investigate rather than a guess based on the current balance.

The result depends on having the right chain and all three addresses before you compare events. Each field narrows the search: the token identifies the event-emitting contract, and owner plus spender identify the permission relationship. You are ready to assess provenance when a successful receipt contains an Approval event from that token with the matching owner and spender. If no such event appears, record the gap: the history may be incomplete, the chain or address may be wrong, or the approval may not follow the ERC-20 event pattern.

Related questions

Which website requested my approval?

Onchain records rarely establish which website prompted an approval. The transaction and event can identify the contract permission and its history, but they do not reliably name the interface a wallet user visited. Treat a website attribution as a separate lead, not as a conclusion from the Approval event.

Can others trace my approvals?

Yes. Public blockchain records let others inspect approval events and their transactions. Matching addresses can reveal the permission history even when a wallet owner uses a tool such as revokecash to review it privately in context.

Why does an explorer show an unknown method?

An explorer may lack the contract metadata or decoding information needed to label a transaction’s input. The method name can therefore be unclear even when the transaction receipt and Approval logs remain available to inspect.

  • Match the chain, token, owner and spender.
  • Save each transaction hash with its log index.
  • Confirm the successful receipt and matching Approval fields.
  • Order events to distinguish the first grant from later updates.
